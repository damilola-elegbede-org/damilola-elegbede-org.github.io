A Lo Cubano Boulder Fest: ticketing and event platform

A full-stack ticketing, check-in and admin platform I built and run for a Cuban salsa festival in Boulder, Colorado. It sells real tickets, so the purchase path is treated as production at all times. Live site: https://www.alocubanoboulderfest.org

Problem

A volunteer-run festival needs to sell tickets, take donations, email attendees, and scan people in at the door, without a platform team and without losing money or overselling a capped event. Traffic is spiky: quiet most of the year, then heavy around on-sale and festival day. The previous setup was a static site plus manual work.

What had to be true:

  • Never sell more tickets than exist, even when many people check out at once.
  • Never lose a paid order, even if the customer closes the tab or an email fails.
  • Door staff scan QR codes on phones, fast, and a ticket cannot be admitted twice by accident.
  • Money reported in the admin dashboard must match what the payment provider says.
  • A small team can operate it, so recovery has to be documented and rehearsed.

Architecture

Components

  • Static front end (vanilla JS, with a small React/Vite layer for some pages) served from Vercel's CDN.
  • About 90 serverless API functions on Vercel: checkout, payments, tickets, wallet passes, QR validation, admin, scheduled jobs.
  • libSQL on Turso as the system of record, with 86 versioned SQL migrations applied at deploy time.
  • Stripe and PayPal for payments. Brevo for email. Apple Wallet and Google Wallet for passes. Sentry for errors.
  • Scheduled jobs for reservation cleanup, email retry, delivery monitoring, event status, and audit retention.

Data flow (purchase)

  1. The browser cart calls the API. The server checks availability and places a time-limited reservation in one atomic database batch.
  2. The customer pays through Stripe or PayPal on the provider's hosted flow, so card data never reaches my servers.
  3. The provider calls a webhook. The server verifies the signature, records the raw event first (idempotency), then creates tickets.
  4. Ticket creation is idempotent, so the webhook, the success redirect and retries all converge on the same result.
  5. A confirmation email goes out with a failed-send retry queue. The ticket gets a signed QR code and optional wallet pass.

Data flow (door) Scanner calls the validate endpoint. A compare-and-swap update marks the scan, so concurrent scans of one ticket cannot both succeed.

Trust boundaries

  • Browser to API: untrusted input, validated on the server; the server is the authority on price, stock and ticket status.
  • Payment provider to webhook: only signed events are accepted.
  • Admin area: separate session, multi-factor sign-in, CSRF protection, rate limiting, audit log of every action.
  • Ticket holders: access via short-lived, scoped credentials, not account passwords.

Key design decisions

  1. Reserve first, fulfil on a verified webhook. Stock is held for 30 minutes in an atomic batch, and tickets are only created when the provider confirms payment. Tradeoff: more moving parts than "create ticket on redirect", and abandoned carts briefly hold stock (a cron releases them). In return, overselling needs a race that the database refuses.
  2. Idempotency everywhere money moves. Raw payment events are stored before processing, and ticket creation is create-or-retrieve. Tradeoff: extra tables and some duplicated-looking writes. Benefit: webhook retries, double clicks and the success page racing the webhook are all safe.
  3. Serverless plus SQLite-family database instead of servers. No machines to patch and cost near zero off-season. Tradeoff: cold starts, connection handling, and no automated down-migrations (SQLite DDL limits). I handle that with a promise-based lazy singleton for connections, a destructive-migration guard, and tiered backups.
  4. Plain JavaScript front end. Smaller payload for people on phones in a crowd. Tradeoff: less structure than a framework, so I rely on contract tests that catch cross-file mistakes a framework would catch at compile time.
  5. Tests that prove gates fire. After several CI checks turned out to be green while testing nothing, I added tests for the gates themselves and fail-closed behavior on truncated runs. Tradeoff: more CI code to maintain.

Stack

  • Front end: HTML/CSS/vanilla JS, React 19 + Vite for some pages
  • Back end: Node 22 serverless functions on Vercel
  • Data: Turso (libSQL), SQL migrations, Vercel Blob for backups
  • Payments: Stripe, PayPal
  • Email and passes: Brevo, Apple Wallet, Google Wallet
  • Quality: Vitest (unit and integration), Playwright (E2E, axe accessibility), ESLint/HTMLHint/markdownlint, k6 load test, Sentry
  • CI/CD: GitHub Actions, Vercel preview deployments

Outcomes

  • Shipped and running a live public site that sells tickets for real events (spring 2026 festival plus smaller weekender events).
  • 505 merged pull requests between July 2025 and October 2026, with a single-digit-day cadence of small, reviewed changes.
  • About 8,000 automated test cases across ~455 test files (unit, integration, E2E); counted statically, see evidence.
  • Pre-festival load test: 60 concurrent QR scans completed in 401 ms with zero 5xx errors and no double-admits (compare-and-swap).
  • Written go/no-go checklist, go-live runbook, incident-response and event-day monitoring runbooks before the 2026 festival.
  • Three-tier database recovery: point-in-time restore (24h), daily compressed dumps (30 days), monthly branches (12 months). Documented targets: recovery in under 5 minutes for same-day mistakes, under 24 hours of data loss in the worst tier.
  • Recent hardening work: removed an unauthenticated ticket-edit route, moved a ticket-view credential out of the URL, removed a preview-environment MFA bypass, stopped logging attendee data. Each was found by audit, fixed with a regression test.
  • Honest note: branch protection does not yet require status checks; I documented that gap and the fix in the repo rather than hiding it.
