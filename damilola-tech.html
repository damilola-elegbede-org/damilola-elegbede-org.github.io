damilola.tech: an AI résumé pipeline that is not allowed to make things up

Live: https://damilola.tech

One-line pitch

A portfolio site with a working AI toolchain behind it: fit scoring, tailored résumés, and cover letters, built so that every claim the model makes about my career has to be traceable to a source I wrote.

Problem

Applying well to senior roles means reading a job description, deciding if it is worth the time, and tailoring a résumé and cover letter. LLMs make that fast, and also make it easy to produce a résumé that sounds strong and is partly invented. A fabricated metric in a résumé is worse than a bland résumé.

So the question I set out to answer was not "can a model write this?" It was "what has to be true of the system so I can trust what comes out?"

Architecture

The site is a Next.js app on Vercel. The public side is a landing page and a chatbot that answers questions about my experience. A separate authenticated surface runs the scoring and generation tools. The same capabilities are also exposed through a key-authenticated REST API and an MCP server, so scripts and agents can use them.

The career source of truth is a private repository of structured and narrative files. It is never committed to this public-facing codebase. It is read at runtime from private object storage, and the model only sees it through server-side code.

Data flow, job description to output

  1. A job description arrives as pasted text or a URL. URLs go through an SSRF validator (blocks private ranges, loopback, link-local, and re-checks redirects).
  2. The fit scorer compares the JD against the full career corpus, not just my one-page résumé. It produces a 0 to 100 score from four weighted components plus hard gates (for example geography and role function). A gate failure scores zero. Gates are not weights.
  3. The résumé generator proposes specific edits to an existing résumé. Each proposed edit passes deterministic gates before it is ever shown or applied.
  4. Surviving edits are re-scored so each one carries a measured effect, then applied. The renderer enforces a two-page cap and trims roles in a defined order if needed.
  5. Output is a PDF, stored privately and served only to authenticated callers.

Trust boundaries

  • Browser to server: public endpoints are rate limited per IP, and the chatbot also has a per-session token budget so rotating IPs does not reset it.
  • Public to authenticated: the admin tools and API sit behind separate session and key-based auth, with CSRF protection on login and lockout on repeated failures.
  • Server to model: the model sees only what the server hands it. Career data and generated PDFs live in private storage, not in the repo and not at guessable public URLs.
  • Model to output: model text is untrusted until it passes the gates described below.

Key design decisions

1. Quotes must be verifiable, or the score is zero. The résumé rubric scores each dimension in its own model call, and every score must cite verbatim text from the source. The server checks that the quote actually appears. An uncited or unverifiable score is clamped to zero rather than treated as "low confidence." Tradeoff: some faithful quotes get rejected because the model cleaned up formatting. I fixed that with a normalizing matcher and then deliberately kept a single matcher for the whole codebase, after finding two copies had drifted apart and one was silently discarding good evidence.

2. Constrain the model, do not average it. The research I read before building this showed that LLM rubric scores are systematically biased, and that repeated runs do not average the bias away. So the rubric is locked and versioned, each dimension is scored separately (removes criteria-order bias), score options are permuted per call from a deterministic seed (removes position bias, stays reproducible), and the score ceiling is computed arithmetically instead of asked of the model. Tradeoff: more calls per score, higher cost and latency.

3. Refuse to emit false precision. The pairwise-anchoring module returns a band and an explicit "not calibrated" flag. It will not produce a point score until it has been validated against real outcomes (my actual callback history). Tradeoff: a less satisfying number today, in exchange for not handing downstream logic a threshold comparison that the evidence cannot support.

4. Deterministic gates around a probabilistic generator. Every proposed résumé edit is checked by plain code: does the original text exist in the résumé, does the new text share a term with the JD, does it invent a quantity that was not in the source. When an accepted edit fails to change the document, it is reported, not swallowed. A regex-and-rules layer is less clever than a second LLM judge, and also predictable, testable, and cheap.

5. Fail loudly when the data is missing. If the career corpus cannot be loaded, scoring errors out. It does not quietly fall back to the résumé, because that would produce a plausible but lower score and a false negative nobody would see. The cover-letter path treats the same failure as non-fatal, since a missing context only weakens prose and does not corrupt a number. Same failure, different handling, chosen per output type.

Stack

  • Next.js (App Router), React, TypeScript in strict mode, Tailwind CSS
  • Anthropic Claude models via the Anthropic SDK and the Vercel AI SDK, with a stronger advisor model consulted by the primary model on résumé generation (bounded use count, with a retry path that drops the advisor if it truncates)
  • Vercel for hosting and cron; Vercel Blob (private and public tiers) for storage; Upstash Redis for distributed rate limiting
  • @react-pdf/renderer and pdf-lib for résumé PDFs and page counting
  • Model Context Protocol server so agents can call the tools
  • Vitest, React Testing Library, Playwright; GitHub Actions

Outcomes

  • Test suite: roughly 3,300 unit and integration test cases across about 215 test files, plus about 130 Playwright end-to-end tests across 13 specs. (Counted by source scan, not by a test run.)
  • Delivery: 264 merged pull requests since January 2026, with changes landing through CI-gated PRs.
  • CI gates on every PR: lint, type check, unit tests with coverage, production build, résumé schema validation, a repository-wide PII scan, a check that no workflow job lacks a timeout, a copy gate that fails the build if public text advertises bypassing employer systems, and a score regression harness run against saved job-posting fixtures from three applicant-tracking systems.
  • Scheduled checks: daily jobs for content drift between the private corpus and storage, for exposure of private blobs, and for the repository accidentally becoming public.
  • Guard tests that encode past mistakes: a test that fails if any call to the current model sets a parameter it rejects; a test that fails if any production file reads career data through the public path.
  • Not measured: no accuracy benchmark or user-outcome numbers exist for the scoring yet. The calibration work against real application outcomes is explicitly still open, and the code says so.
