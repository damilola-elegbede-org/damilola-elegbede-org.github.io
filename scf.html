Sabor Con Flow Dance: a small-business site, rebuilt and hardened

I rebuilt a Boulder salsa studio's website from a legacy Django app into a Next.js site on Vercel, with a CSP, rate-limited public forms, a moderated testimonial pipeline, and a CI gate on lint, build, types and tests.

Problem

Sabor Con Flow is a small dance studio that teaches Cuban salsa and casino classes. The owner needs a site that explains classes and pricing, takes private-lesson bookings, collects student testimonials, and answers contact requests, without anyone running a server. The previous site was a Django app on a self-managed host, which was more to maintain than a studio should carry. The site also takes input from the public (forms, testimonials), so it needed basic abuse protection and a way for the owner to approve what appears on the page.

Architecture

The site is one Next.js (App Router) application on Vercel. Most pages are static content rendered from typed data files (classes, pricing, FAQ, gallery, SEO). Three things need a server: the contact form, testimonial submission, and class booking requests. Those go through server routes and actions backed by a managed Postgres database and a transactional email service. Private-lesson scheduling is delegated to a third-party embedded scheduler. The hero video is served from object storage, not the app.

Trust boundaries: everything from a browser is untrusted. Public form endpoints validate input, drop honeypot hits, and are rate limited per IP. The moderation area sits behind an edge auth check, and each server action re-checks credentials, so the actions are not reachable just because the route guard was skipped. A strict Content Security Policy limits which external origins can load scripts, frames, images and media.

Key design decisions

  1. Rewrite instead of patching the Django site. The 2.0.0 changelog records a full rebuild in Next.js, TypeScript strict mode and Tailwind 4, hosted on Vercel. Tradeoff: a rewrite costs more up front and drops the old stack's features, but it removes server upkeep for a business with no engineer on staff.
  2. Rate limiting in the existing Postgres, not a new service. Each submission is inserted first, then counted over a one-minute window (limit 5 per IP), so concurrent requests cannot all read a low count and slip through. Old rows are cleaned up opportunistically. Tradeoff: it adds a write to every submission and is coarser than a dedicated edge limiter, but it adds no new vendor or cost. The code skips limiting when no database is configured, which is convenient locally and a risk if production is ever misconfigured.
  3. Defense in depth on the moderation area. The route is guarded at the edge, and every server action checks authorization again. Tradeoff: a second check on each action costs a little latency, but a missed edge rule can never expose a write path on its own.
  4. A strict content security policy, maintained by regression. The policy blocks framing, restricts where forms can post, and allows only the scheduling widget and media storage. Tradeoff: every new third-party embed needs a deliberate policy change, which slowed a couple of releases and was worth it.
  5. Keep private links out of page source. The community invite link is served through a server redirect, so it is not in the HTML or shipped JS. Tradeoff: one extra hop, and anyone who follows the redirect still learns the link, so this reduces scraping and does not make the link secret.

Stack

Next.js 16 (App Router), React 19, TypeScript (strict), Tailwind CSS 4. Managed Postgres for testimonials, bookings and rate-limit state. A transactional email API for the contact form. An embedded third-party scheduler for private lessons. Vercel hosting, Analytics and Speed Insights, with object storage for video. Vitest, Testing Library and MSW for tests. GitHub Actions for CI, plus CodeQL and Dependabot workflows.

Outcomes

  • Live at https://www.saborconflowdance.com (returned HTTP 200 when checked).
  • 46 merged pull requests between September 2025 and September 2026, and the git history runs from July 2025.
  • 10 test files with 45 passing tests, covering the CSP, the rate limiter, the redirect route, pricing, the contact and booking forms, and key pages.
  • CI on every push and pull request runs lint, production build, type check and tests as separate jobs, with read-only token permissions. CodeQL and Dependabot runs were green on main at last check.
  • Security headers shipped site-wide: CSP, HSTS, no-sniff, frame denial, referrer and permissions policies.

Not measured: no Lighthouse or performance numbers are recorded in the repo, and I am not claiming any. There is no traffic, conversion or revenue data here. Test coverage percentage is not recorded. Payments are not live: bookings are stored as pending requests and checkout is not wired up. This is a single-studio site with a small amount of traffic, not a high-scale system.
